# Isolated restoration rehearsal

This procedure is for the disposable loopback development rehearsal, not a production restore. No source database, existing project, or production schedule is replaced. `tools/backup/restore.py` refuses the development container, arbitrary names and nonempty targets. A production recovery needs separately authorized maintenance and destination setup; this utility intentionally does not accept hosted destinations.

1. Confirm Docker and the existing local Supabase are healthy, with no business/Auth data. The test harness refuses a populated source and never runs against a hosted URL. Do not reset or delete an environment containing intended data to satisfy that check.
2. Run the managed-account fixture suite and rehearsal from this repository:

   ```powershell
   python tools/tests/t03_api.py --corrections --reports --reports-functional --outputs --documents --restore
   ```

   The restore subprocess uses the existing bundled Python with the pinned T16 cryptography dependency. It provisions only synthetic accounts, operations, corrections, documents and private receipt objects. Credentials pass in memory, never command-line arguments or evidence. Ignored artifacts remain in `tools/.local/t17-rehearsal-<UUID>`.
3. T16 creates an encrypted database/Auth archive and content-addressed encrypted receipt blobs. A separate wrapped recovery file is protected by a separately held passphrase. The test deletes the original Windows vault encryption key before attempting recovery. Wrong-passphrase and integrity checks precede destination writes. Copy **archives and objects** together when recovering; a database dump or archive directory alone is incomplete.
4. A new `carrier_restore_<random>` Supabase project uses port the probed isolated API port (57321 in the verified run) and independent containers/volumes. It has the same installed PostgreSQL/provider versions, disabled public signup and the staff token hook. Auth, REST and Storage services are stopped while restoring.
5. Reconstruct the NOLOGIN/NOBYPASSRLS application roles. In this verified empty disposable target only, replace its provider baseline database with a pristine `template0` database owned by postgres. Keep the default public schema. Restore the full custom dump with `pg_restore --single-transaction --exit-on-error`, preserving ownership, ACLs, policies, functions, triggers and migration history. Restore recorded membership options. Do not use `--clean` to replace a bootstrapped provider schema: inherited Realtime partition constraints cannot be dropped that way.
6. Remove obsolete target sessions and refresh tokens (their data was excluded by T16). Compare schema and complete application/identity record fingerprints, office assignments, exact journal balances, original/reversal records and immutable document snapshots. Canonical comparison uses a common empty search path and sorted ACLs.
7. Storage database metadata does not restore file bytes. Keep the copied provider object rows and upload/upsert every verified decrypted object to its private bucket using the restored receipt MIME references. Keep application receipt/evidence references and hashes unchanged. Download and independently verify every file's size/SHA-256 and test assigned, unassigned and anonymous access.
8. Reject old access/refresh tokens; authenticate freshly using the restored identities and password hashes. Verify staff mappings, office RLS and direct-write denial. Check issued-document snapshot equality and the digest-checked reprint API. Refuse a second restore into the now-populated target.
9. Record measured recovery time, counts and results. The rehearsal removes its unique target containers/volumes and temporary vault entries in `finally`. Confirm source health and fixture cleanup. No production schedule is registered.

Recovery material should be retained off the original PC, separately from encrypted backups, with its passphrase separately protected. The rehearsal simulates losing the vault key; it does not simulate physical hardware loss or prove hosted-project migration across differing provider versions. Local provider services are reconstructed from installed versions/configuration, not recovered from database rows. Required public client/backend settings, managed role credentials, Auth signing material and service secrets must be supplied securely for a real new environment. Supabase Vault/column encryption, SSO and external OAuth are outside this v1.

References: [PostgreSQL pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html), [Supabase manual backup and restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore). Actual executed results and discovered failures are recorded separately in restoration-evidence.md.

Startup diagnosis: capture CLI JSON errors as well as text, inspect Docker State/Health and provider endpoints, and check Windows excluded TCP ranges (`netsh interface ipv4 show excludedportrange protocol=tcp`). Do not bypass health checks or authentication. The runner probes all ten ports of a separate candidate block before creating target configuration; occupied/reserved blocks are skipped, and no available block fails closed. It never alters Windows reservations or source ports. Backup metadata records runtime image tags without container environment credentials; the runner reuses compatible installed images and verifies image IDs before restoration. Preserve encrypted archives and separately protected recovery material across failed attempts.
